What is a REST API?
The foundation — understand this and everything else clicks.
🍽️ Real-world analogy

Think of a REST API like a restaurant menu. You (the client) don't go into the kitchen — you just look at the menu (API docs), place an order (send a request), and the waiter brings back your food (the response). You never need to know how the kitchen works.

🌐 REST = Rules for talking over the web

REST stands for Representational State Transfer. It's not a tool or software — it's a set of rules (an "architectural style") for how computers should communicate over the internet using HTTP.

📦 API = The door to someone's data or service

An API (Application Programming Interface) is how one application exposes its functionality to others. A REST API does this over HTTP — the same protocol your browser uses.

📋 6 Principles of REST

1. Client-Server — The client and server are separate. Your code doesn't care how the server stores data.
2. Stateless — Every request is self-contained. The server doesn't remember your previous request. You send everything needed each time.
3. Uniform Interface — Every API follows the same conventions (URLs, methods, JSON). Learn one, learn them all.
4. Cacheable — Responses can be cached to speed things up.
5. Layered System — There can be proxies, gateways, or load balancers between you and the server — you don't need to know.
6. Resource-Based — Everything is a resource with a URL. A user, an order, a product — all resources.

🔗 URLs = Resources

In REST, every piece of data is a resource with its own URL (called an endpoint):

# A collection of users https://api.example.com/users # A specific user (id = 42) https://api.example.com/users/42 # That user's orders https://api.example.com/users/42/orders
HTTP Methods (Verbs)
Methods tell the server what action you want to perform.
📁 Analogy

Think of a database table of users. The URL /users is the resource. The HTTP method tells the server whether you want to read, create, update, or delete that resource — like CRUD operations.

GET Read / Fetch data

Retrieve a resource. Does not change anything on the server. Like a SELECT in SQL.

# Get all users GET /users # Get a specific user GET /users/42

POST Create new data

Send data to the server to create a new resource. Like an INSERT in SQL.

POST /users # with body: { "name": "Alice", "email": "alice@example.com" }

PUT Replace / Update (full)

Replace an existing resource completely. Like UPDATE ... SET all columns in SQL.

PUT /users/42 # with body (send ALL fields): { "name": "Alice Smith", "email": "alice@new.com" }

PATCH Update (partial)

Update only specific fields of a resource. Like UPDATE ... SET one column in SQL.

PATCH /users/42 # Only update the email: { "email": "alice@updated.com" }

DELETE Remove data

Delete a resource from the server. Like DELETE FROM in SQL.

DELETE /users/42 # No body needed — just the URL

Request & Response
The anatomy of every API call you'll ever make.

📤 Anatomy of an HTTP Request

Every request has these parts:

# 1. METHOD + URL (endpoint) POST https://api.example.com/users # 2. HEADERS (metadata about the request) Content-Type: application/json Authorization: Bearer eyJhbGci... X-API-Key: my-secret-key-123 Accept: application/json # 3. BODY (data you send — only for POST/PUT/PATCH) { "name": "Alice", "email": "alice@example.com" } # 4. QUERY PARAMS (filters, pagination — for GET) /users?page=2&limit=50&status=active

📥 Anatomy of an HTTP Response

Every response has a status code + a JSON body:

# Status line HTTP/1.1 201 Created # Response headers Content-Type: application/json X-Request-Id: abc-123 # Response body (JSON) { "id": 99, "name": "Alice", "email": "alice@example.com", "created_at": "2026-03-06T10:00:00Z" }

🔑 Common Headers Explained

Content-Type: application/json — "I'm sending JSON data"
Accept: application/json — "Please give me JSON back"
Authorization: Bearer <token> — "Here's my auth token"
X-API-Key: <key> — "Here's my API key"

🔎 Query Parameters vs Body

QUERY PARAMS

Appended to the URL. Used for filtering, sorting, pagination. Used with GET.

/orders?status=paid&limit=100&page=3
REQUEST BODY

JSON sent inside the request. Used for creating or updating data. Used with POST/PUT/PATCH.

{"status": "paid", "amount": 99.99}

🐍 Python Example (requests library)

import requests # GET with query params response = requests.get( "https://api.example.com/orders", headers={"X-API-Key": "my-key"}, params={"status": "paid", "limit": 100} ) data = response.json() # Parse JSON response # POST with body response = requests.post( "https://api.example.com/users", headers={"X-API-Key": "my-key"}, json={"name": "Alice", "email": "alice@x.com"} ) print(response.status_code) # 201 print(response.json()) # {"id": 99, "name": "Alice", ...}
HTTP Status Codes
The server's way of telling you what happened.
📬 Analogy

Status codes are like delivery notifications. 200 = "Delivered successfully." 404 = "Address not found." 500 = "Our truck broke down."

2xx — Success
200
OK
Request succeeded. Data returned.
201
Created
New resource created (POST success).
204
No Content
Success, but no body returned (DELETE).
4xx — Client Errors (your fault)
400
Bad Request
Invalid data sent (e.g. missing field).
401
Unauthorized
Not authenticated. Check your API key.
403
Forbidden
Authenticated but no permission.
404
Not Found
Resource or endpoint doesn't exist.
422
Unprocessable
Validation failed on your data.
429
Too Many Requests
Rate limited. Slow down your calls!
5xx — Server Errors (their fault)
500
Internal Server Error
Something broke on their end.
503
Service Unavailable
Server is down or overloaded.

🐍 Handle Status Codes in Python

response = requests.get("/users/42", headers=HEADERS) if response.status_code == 200: data = response.json() elif response.status_code == 401: raise Exception("Invalid API key!") elif response.status_code == 404: print("User not found") elif response.status_code == 429: print("Rate limited — slow down!") # Or use raise_for_status() to auto-raise on 4xx/5xx response.raise_for_status()
REST APIs in Data Engineering
How you'll actually use this day-to-day.

🔄 Pattern 1: Extracting Data (ETL)

The most common use — pulling data from external systems into your data warehouse.

import requests, pandas as pd def extract_orders(api_key, start_date): all_orders = [] page = 1 while True: response = requests.get( "https://api.shopify.com/orders", headers={"X-Shopify-Access-Token": api_key}, params={"created_at_min": start_date, "limit": 250, "page": page} ) data = response.json()["orders"] if not data: break # No more pages all_orders.extend(data) page += 1 return pd.DataFrame(all_orders)

⏱️ Pattern 2: Pagination

APIs limit how many records they return at once. You need to loop through pages.

Offset pagination: ?page=1&limit=100 → ?page=2&limit=100
Cursor pagination: Response includes a next_cursor token to pass in the next request.
Link header pagination: Response headers include a Link: <url>; rel="next"

🚦 Pattern 3: Rate Limiting

APIs limit how many calls you can make. Ignore this and your pipeline will break.

import time def safe_get(url, headers, params=None): for attempt in range(3): # Retry 3 times r = requests.get(url, headers=headers, params=params) if r.status_code == 429: # Rate limited wait = int(r.headers.get("Retry-After", 60)) print(f"Rate limited. Waiting {wait}s...") time.sleep(wait) continue r.raise_for_status() return r.json() raise Exception("Max retries exceeded")

🛠️ Pattern 4: Webhooks (APIs calling YOU)

Instead of polling an API constantly, you can register a webhook URL. The service will call your endpoint when something happens (e.g., new order placed). Common in event-driven pipelines.

Polling: You ask "any new data?" every 5 minutes → inefficient
Webhook: They call your endpoint the moment new data arrives → efficient
